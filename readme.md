# POLYRUST: лендинг и референсный CCIP-модуль

В репозитории находятся две независимые части: публичный лендинг POLYRUST и экспериментальный модуль мультичейн-платежей `ccip-payments`.

> **Важно: `ccip-payments` — проектный прототип и архитектурный референс, а не готовое production-решение.** Его следует использовать как основу для обсуждения, тестирования и дальнейшей разработки. Модуль требует доработок, проверки реальных CCIP-маршрутов и независимого аудита до работы с настоящими средствами.

## 1. Лендинг

Публичный одностраничный сайт POLYRUST на React, TypeScript и Vite. Описывает платформу, торговый движок, рынки, партнёрскую программу и подход к прозрачности.

- `src/site/` — компоненты, контент и стили сайта.
- `public/` — статические ресурсы.
- Корневые `package.json` и `package-lock.json` относятся к лендингу.

Запуск из корня репозитория:

```sh
npm ci
npm run dev
```

Проверка production-сборки:

```sh
npm run build
```

### Деплой лендинга на Render

Для статического лендинга этой ветки используй **Static Site**:

- **Branch:** `with_ccip`.
- **Root Directory:** корень репозитория.
- **Build Command:** `npm ci --include=dev && npm run build`.
- **Publish Directory:** `dist`.

`tsconfig.app.json` проверяет только `src/`, а `tsconfig.node.json` — только `vite.config.ts`. Отдельный проект `ccip-payments` не входит в сборку лендинга. Для деплоя сайта не нужны установка вложенных зависимостей CCIP, `viem` в корневом пакете или ключи кошелька. Не добавляй их только ради устранения ошибок TypeScript.

Сам CCIP-прототип проверяется отдельно из своей папки командами ниже; Solidity-контракт развёртывается в блокчейне, не на Render. Статический сайт не запускает CLI-скрипты и не выполняет деплой контракта автоматически.

**Лендинг не подключён к CCIP-модулю автоматически:** сам по себе он не принимает платежи, не открывает стейкинг-позиции и не выполняет транзакции с кошельком.

## 2. Модуль `ccip-payments`

Отдельный проект со своими зависимостями, конфигурацией, смарт-контрактом, клиентской библиотекой, CLI-скриптами и локальными тестами.

### Что он демонстрирует

- Приём токенов из разных EVM-сетей через Chainlink CCIP с агрегацией денег и статусов заказов на одной главной сети — **Hub**.
- Развёртывание одного прикладного контракта `PaymentHub` на Hub, без контрактов магазина в сетях отправки.
- Отправку платежа напрямую из кошелька: `approve` официальному Router → расчёт комиссии → `ccipSend`.
- Проверку сети-источника, зарегистрированного заказа, токена, точной суммы и повторных сообщений.
- Подключение браузерного EIP-1193-кошелька и асинхронное отслеживание оплаты.
- Учёт обычных оплат и демонстрационный стейкинг с заранее обеспеченной наградой.

### Стейкинг — не источник доходности

Сценарий «внести 100, через неделю получить 110» реализован как **prefunded reward**: администратор заранее вносит 10 токенов награды, пользователь переводит 100, после доставки начинается семидневная блокировка. Депозит и награда резервируются; по окончании срока пользователь может получить 110 на Hub либо отправить их обратно в исходную сеть через CCIP.

**CCIP только доставляет токены и сообщения — он не генерирует прибыль.** Здесь нет работающей инвестиционной стратегии или интеграции доходного протокола. Награда обеспечивается средствами администратора, а комиссии и gas оплачиваются отдельно.

### Токены и сети

- Приёмочный testnet-сценарий: **10 USDC, Base Sepolia → Arbitrum Sepolia**.
- Mainnet-каталог содержит маршруты USDC и GHO из 13 сетей отправки в Arbitrum One по снимку официального CCIP Directory.
- Не каждый токен доступен в каждой сети. Заказ фиксирует одну разрешённую валюту и сумму; автоматической конвертации или swap нет.
- Каталог не означает, что production-маршруты уже протестированы. Адреса, доступность направлений, token pools и лимиты необходимо перепроверять перед использованием.

### Структура

```text
ccip-payments/
├── contracts/       # PaymentHub и локальные тестовые контракты
├── src/             # Viem-клиент оплаты, подключение кошелька, ABI
├── config/          # Снимок сетей, токенов и маршрутов CCIP
├── scripts/         # Деплой, регистрация заказа, оплата, статус, вывод
├── test/            # Локальные тесты контракта и клиента
├── ccip_usage/      # Подробное описание задачи и инструкции
└── .env.example     # Пример локальных настроек без секретов
```

### Локальная проверка

Перейти в каталог `ccip-payments` и выполнить:

```sh
npm ci --ignore-scripts --legacy-peer-deps
npm run compile
npm run typecheck
npm test
```

Модулю требуется Node.js 22+. Локальные тесты проверяют логику контракта и клиента, но **не заменяют реальный межсетевой перевод**.

Пошаговые инструкции по testnet, стейкингу, браузерному использованию и mainnet находятся в **[ccip-payments/ccip_usage/README.md](ccip-payments/ccip_usage/README.md)**.

## 3. Что нужно доработать

Перед превращением референса в рабочий продукт необходимо:

1. **Уточнить границы компонентов:** разделить смарт-контракт, платёжный SDK, backend учёта заказов, checkout UI и сервис мониторинга.
2. **Пересмотреть конфигурацию:** текущий JSON-каталог и `.env.example` — начальная схема. Нужны отдельные настройки сред, валидация конфигов, управление секретами, актуализация адресов и реестр деплоев.
3. **Реализовать Web2-интеграцию:** базу заказов, авторизацию админ-операций, надёжную обработку событий и защиту от повторных действий. Выдавать товар только после подтверждённой оплаты на Hub.
4. **Добавить эксплуатационные процессы:** восстановление после неудачной доставки, разбор дублирующих платежей, управление бюджетом наград и неоплаченными стейк-заказами. Автоматического возврата или отмены таких заказов в прототипе нет.
5. **Проверить экономику:** источники наград, комиссии, риск де-пега, ограничения токенов, правовые и налоговые требования.
6. **Выполнить настоящий testnet-тест туда и обратно**, проверить выбранные mainnet-маршруты, устранить риски зависимостей и провести независимый аудит.

### Возможный перенос части системы на Rust

Текущая реализация использует Solidity для EVM-контракта и TypeScript/Viem для клиента и скриптов. После уточнения архитектуры **можно рассмотреть Rust для backend-сервисов, мониторинга, индексирования событий и CLI**.

Это не означает буквального переноса EVM-контракта на Rust: совместимость с выбранной сетью, CCIP-интерфейсами и моделью исполнения нужно оценивать отдельно. При сохранении этой EVM-архитектуры контракт остаётся Solidity-компонентом, а браузерный кошелёк требует соответствующей клиентской интеграции. Rust — возможное направление дальнейшей разработки, а не уже выполненная миграция.

## 4. Безопасность и статус

- Реальный деплой и приёмочный межсетевой перевод в рамках реализации не выполнялись.
- Использовать только тестовые кошельки и средства до завершения проверок и аудита.
- В build/test-зависимостях есть предупреждения `npm audit`; они требуют отдельного review.
- Вложенные `node_modules`, `.env` с секретами, артефакты сборки и локальные данные деплоя исключены из Git.
- Не размещать приватные ключи в коде, README, коммитах или браузерном приложении.

**Итог:** лендинг — публичная презентационная часть; `ccip-payments` — отдельный проектный прототип для исследования мультичейн-платежей и обеспеченных наград. Его нельзя воспринимать как готовый финансовый продукт.
